## Commands

- Run the dev server: `flask run` (reads `FLASK_APP`/`FLASK_DEBUG` from `.env` automatically via python-dotenv)
- Apply schema changes: `flask db migrate -m "..."` then `flask db upgrade`
- Generate a member invite link: `flask create-invite` (prints a token/path; prepend the host to visit it) — or, once at least one admin account exists, via the web UI at `/admin/invites` (also supports revoking an unused invite and setting an optional expiration date, neither of which the CLI command offers)
- Rebuild Tailwind CSS after editing templates or classes: `npx @tailwindcss/cli -i ./app/static/src/input.css -o ./app/static/css/output.css --minify` (swap `--minify` for `--watch` during active template work — compiled CSS is committed to git, so forgetting to rebuild means styling changes silently don't appear)
- Build/run the production Docker image locally: `docker build -t sb-bookclub-app .` then `docker run -e SECRET_KEY=... -e SQLALCHEMY_DATABASE_URI=... -e FLASK_DEBUG=0 -p 8080:8080 sb-bookclub-app` — see `docs/deployment.md` for the full Cloud Run + Neon deploy runbook
- Apply a migration to the production database: point `SQLALCHEMY_DATABASE_URI` at the production Postgres URL and run `flask db upgrade` from your own machine (Cloud Run has no release-phase hook) — see `docs/deployment.md`
- No automated test suite exists yet. No linter/formatter is configured (pylint/black were discussed but never installed).

## Architecture

**App factory + blueprints**: `app/__init__.py`'s `create_app()` wires config, three extensions (`db`, `migrate`, `login_manager` — all instantiated unbound in `app/extensions.py`, then `.init_app()`'d here to avoid circular imports with `models.py`), imports `app/models.py` once (required so Alembic's autogenerate can see the model classes — they're otherwise never imported anywhere in the factory's chain), and registers three blueprints: `auth` (`app/auth/`), `books` (`app/books/`), and `admin` (`app/admin/`). Each blueprint package has `routes.py` (the `Blueprint` object + views) and `forms.py` (Flask-WTF forms); `__init__.py` just re-exports `bp` from `routes.py`.

**Models** (`app/models.py`): `Member` (`is_admin` now actually gates something — see the admin portal below), `Invite` (one-time registration tokens — created either via the `flask create-invite` CLI command or the `/admin/invites` web route, both funneling through the same `Invite.create(expires_at=None)` staticmethod so the creation logic lives in one place), `PasswordReset` (one-time password-reset tokens, admin-generated only, see below), `Book`, `Rating`, and the `BookStatus` enum. `Book`'s title column is named `name`, not `title` — a naming mismatch from early development that was never renamed; forms/routes map between them (`Book(name=form.title.data, ...)`), it's intentional-by-inertia, not a bug.

**Auth is invite-only self-registration**, not manual seeding: an `Invite` row is created (token auto-generated via `secrets.token_urlsafe`), and `/auth/register/<token>` validates it (exists, unused, unexpired via `Invite.is_expired`) before letting someone create their own `Member`. `display_name` defaults to `username` at registration — there's no separate field for it; changing it later is still an unbuilt feature. The login page (`/auth/login`) redirects straight to `home` if already authenticated, and has two inline "Have a token?" panels (invite / password reset) that let someone paste a bare token and get redirected to the right `/auth/register/<token>` or `/auth/reset-password/<token>` URL client-side — the existing route validation handles anything invalid, so there's no separate token-lookup endpoint.

**Admin portal** (`app/admin/`, routes gated by a local `admin_required` decorator stacked under `@login_required`): `/admin/invites` lists every invite with a computed `Invite.status_label` (Pending/Used/Expired) and lets an admin generate one (with an optional expiration date) or revoke an unused one (hard delete, not a soft-revoke flag — there's no `revoked_at` column). `/admin/members` lists every member and lets an admin generate a password-reset link for one; generating a new one first deletes that member's other unused `PasswordReset` rows, so at most one is ever valid per member. Both pages show the token and the full URL side by side with "Copy" buttons (`data-copy-value`, wired in `app/static/js/admin.js`) since either form is useful to hand someone directly.

**Password reset** (`app/models.py`'s `PasswordReset`, `/auth/reset-password/<token>` in `app/auth/routes.py`): admin-only generation (no self-service "forgot password" request flow — there's no email integration to build one on top of), fixed 24-hour expiration (`PasswordReset.create(member)`, not admin-configurable, unlike `Invite.expires_at`), and the same not-found/used/expired validation shape as `register()`. Completing a reset updates the existing `Member`'s password in place and logs them in immediately, mirroring `register()`'s post-submit behavior.

**Book edit/delete permission**: `current_user.id == book.picked_by_id or current_user.is_admin` (helper: `_can_manage()` in `app/books/routes.py`) — the person whose turn it was to pick the book, or an admin. Delete additionally refuses if the book has any ratings, to preserve reading history. Ratings themselves have no delete route at all (by design) — `book_detail()` is a combined GET/POST view that *upserts*: looks up any existing `Rating` for `(book_id, current_user.id)` and updates it in place, or creates one if none exists. `book_detail()` also computes `newer_book`/`older_book` (the prior/next book by `reading_start_date`, via the same `_sort_books()` helper the list view uses) and passes them to the template for the prev/next nav links.

**Book list default ordering**: `GET /books/` defaults to `?sort=reading_first` (`_sort_books()` in `app/books/routes.py`), which stable-sorts by date first and then by a fixed status priority (`_LIST_STATUS_ORDER = [CURRENTLY_READING, TO_BE_READ, FINISHED, ABANDONED]`) so Currently Reading books always sort first; the `book_card` macro (`_macros.html`) gives those an amber border via its `highlighted` param. Explicitly choosing "Start date" / "Status" / "Average rating" from the sort dropdown is unaffected by this and behaves as it always has.

**WTForms gotcha worth knowing before adding more form fields**: `SomeForm(obj=some_model)` pre-fills fields by matching attribute names on the object. This breaks silently (no error, just wrong pre-filled value) whenever a form field's name doesn't line up 1:1 with a plain column — e.g. `BookForm.status` needs `book.status.name` (the object holds an enum member, the field expects the enum's string name), `BookForm.picked_by` needs `book.picked_by_id` (the object's matching-named attribute is a relationship returning a `Member`, not the FK int the field expects), and `BookForm.title` needs `book.name` (different attribute names entirely, per the mismatch above). `edit_book()` in `app/books/routes.py` overrides all three explicitly, guarded by `if request.method == "GET":` so the override doesn't clobber a real POST submission. Follow this pattern for any new form field backed by an enum, a relationship, or a differently-named column.

**CSRF on non-FlaskForm actions**: Flask-WTF's CSRF protection is per-form-instance (validated via `form.validate_on_submit()`), not a blanket app-wide check — there's no global `CSRFProtect(app)` registered. A plain `<form method="POST">` with no Flask-WTF form behind it (e.g. a bare delete button) gets **no** CSRF protection. The pattern used for the book delete button (`DeleteForm` in `app/books/forms.py` — a fieldless `FlaskForm` that exists purely to carry a token) is the template to follow for any future action-only button; `RevokeInviteForm` and `GenerateResetForm` (`app/admin/forms.py`) are the same pattern applied to the admin portal's action buttons.

**Datetime convention, portable across SQLite and Postgres**: `expires_at`/`created_at`/`used_at` columns are plain `db.DateTime` (no `timezone=True`) and are always written/compared as timezone-*naive* UTC via the shared `_naive_utcnow()` helper in `app/models.py` (`datetime.now(timezone.utc).replace(tzinfo=None)`) — never the deprecated `datetime.utcnow()` (Python 3.12+) and never a raw timezone-aware `datetime.now(timezone.utc)` against these columns (raises `TypeError: can't compare offset-naive and offset-aware datetimes`). This was originally written to compensate for SQLite dropping tzinfo on round-trip; `_naive_utcnow()` makes that behavior intentional and explicit rather than SQLite-specific, so it round-trips identically once deployed against Postgres (`TIMESTAMP WITHOUT TIME ZONE` is naive by column type, not by driver/session-timezone coincidence). Follow the `_naive_utcnow()` pattern for any new expiry-style check.

**Open Library auto-fill** (`GET /books/api/lookup` in `app/books/routes.py`, wired up client-side in `app/static/js/books.js`): one of two outbound HTTP calls this app makes (the other is the cover picker below). Both the `isbn` path and the `title`/`author` fallback path go through the same `search.json` endpoint (Open Library's older `api/books`/`bibkeys` "Books API" 404s as of this writing — `search.json?isbn=...` returns the same title/author/cover data in one call, so it's used for both cases). Given an `isbn`, the first result is treated as an exact match; given `title`/`author` instead, up to 5 candidates are returned for the user to pick from (title/author search alone is ambiguous — there's no guarantee of a single right edition; each candidate row shows its own default cover inline via `_open_library_candidate()`'s `cover_url`, not just behind the "more covers" toggle). Either path always returns `200` with one of `{"match": {...}}`, `{"candidates": [...]}`, or `{"error": "..."}` — network failures and "not found" collapse into the same generic error response (real exceptions are logged server-side via `current_app.logger.warning`, never surfaced to the client) so a slow or unreachable Open Library never blocks manual form entry; requests use a 5s timeout. No API key is required, but Open Library asks for an identifiable `User-Agent` — the contact portion is read from the `OPEN_LIBRARY_CONTACT` env var (falls back to a placeholder if unset) rather than being hardcoded, since it's sent to a third party on every request. Picking a lookup result or an ISBN match always overwrites whatever is currently in the title/author/cover_url/isbn fields (no "fill blanks only" behavior). Cover images (here and in the picker below) are requested at Open Library's `L` size preset (301×500px) rather than the smaller default `M` (180×298px) — `M` looked visibly soft once actually rendered at the book list/detail pages' real display sizes.

**Open Library cover picker** (`GET /books/api/lookup/covers` in `app/books/routes.py`, the "Show more covers" toggle per candidate in `app/static/js/books.js`): `search.json` groups results by *work*, not by edition, so a candidate's default cover (`cover_i`) is just whichever edition Open Library's index happened to pick — often not the printing the user recognizes. This endpoint fetches `/works/{work_key}/editions.json` (up to 200 entries in one call) and filters to English-language editions (or editions with no language tag at all, treated as English — matches observed data) that have real cover art, returning up to 8 as `{"cover_url": ..., "isbn": ...}` pairs. Open Library's public API has **no popularity/ratings signal at the edition level** (checked directly — `ratings.json`/`bookshelves.json` only exist per-work, aggregating all editions), so English-plus-real-cover is the best available proxy, not a true popularity ranking. Each cover is paired with its *own* edition's ISBN (`isbn_13`, falling back to `isbn_10`) specifically so that picking an alternate cover thumbnail updates the ISBN field to match — an earlier version returned bare cover URLs and reused the original candidate's ISBN, which could silently pair a cover with the wrong edition's ISBN; `fillBookFields()` in `books.js` still won't blank the ISBN field out for the minority of editions with no ISBN on record, since its fill helper already no-ops on falsy values. `work_key` (client-supplied, sourced from an earlier Open Library response) is validated against a strict `/works/OL\d+W` regex before being interpolated into the outbound URL. Both this fetch and the main lookup fetch show an inline loading spinner (`createSpinner()` in `books.js`) while in flight — deliberately a different visual (a small circular spinner) from the page-navigation loading bar below, so "this widget is loading" reads differently from "the whole page is navigating."

**Cancel button on add/edit forms** (`app/templates/books/form.html`): `edit_book()` in `app/books/routes.py` passes `book=book` to the template (unlike `add_book()`, which doesn't) so the template can tell the two modes apart — Cancel links back to the book's detail page in edit mode, or the book list in add mode, via `{{ url_for('books.book_detail', book_id=book.id) if book else url_for('books.index') }}`.

**Site-wide page-navigation loading bar** (`#page-loading-bar` in `app/templates/base.html`, `initPageLoadingBar()` in `app/static/js/main.js`): a thin top progress bar shown on any same-origin link click or form submit, to give feedback once the app is deployed somewhere with real server latency (vs. instant on localhost). Deliberately separate from — and visually distinct from — the Open Library widget's own in-place spinners above; site-wide chrome like this lives directly in `main.js` per `docs/js-architecture.md`'s documented convention, not in a blueprint file.

## Data Model

- **Member**: id, username, password_hash, display_name, is_admin
- **Invite**: id, token (unique), created_at, expires_at (nullable — optionally settable from `/admin/invites`), used_at (nullable — null means still valid)
- **PasswordReset**: id, member_id (FK, required), token (unique), created_at, expires_at (fixed 24h after creation, not nullable), used_at (nullable — null means still valid)
- **Book**: id, name (displayed/referred to as "title"), author, cover_url, isbn (nullable, optional — populated via the Open Library auto-fill lookup or typed manually), added_by_id (FK, required), picked_by_id (FK, nullable), created_at, reading_start_date, reading_end_date, status (`BookStatus` enum, has a DB-level `CHECK` constraint)
- **Rating**: id, book_id (FK), member_id (FK), score (float, 1.0–5.0 in 0.5 steps, DB-level `CHECK` constraint), comment, created_at — unique constraint on `(book_id, member_id)`
